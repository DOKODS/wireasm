# Язык WireASM 0.4.0

Граф — это JSON-файл. Узлы лежат в `nodes`, провода в `edges`. Компилятор
читает граф, проверяет его и выдаёт ассемблер для выбранной цели.

## Формат графа

```json
{
  "name": "sum_loop",
  "target": "aarch64-macos",
  "variables": [
    { "name": "acc", "init": 0 }
  ],
  "nodes": [
    { "id": "entry", "kind": "Entry", "x": 40, "y": 240, "props": {} },
    { "id": "one", "kind": "Const", "x": 40, "y": 420, "props": { "value": "1" } },
    { "id": "ret", "kind": "Return", "x": 500, "y": 240, "props": {} }
  ],
  "edges": [
    { "fromNode": "entry", "fromPin": "exec", "toNode": "ret", "toPin": "exec" }
  ]
}
```

Поля:

| Поле | Тип | Обязательно | Смысл |
|---|---|---|---|
| `name` | строка | нет | имя графа и основа имени `out/<name>.s` |
| `target` | строка | нет | `aarch64-macos` по умолчанию; см. цели ниже |
| `variables` | массив | нет | начальные значения переменных, `init` — число u64 |
| `nodes[].id` | строка | да | уникальный идентификатор; из него делается метка `L<id>` |
| `nodes[].kind` | строка | да | тип узла из таблицы ниже |
| `nodes[].x`, `y` | число | нет | позиция на холсте, на код не влияет |
| `nodes[].props` | объект | нет | строковые свойства узла; числа тоже пишутся строкой |
| `edges[].fromNode/fromPin` | строка | да | выходной пин источника |
| `edges[].toNode/toPin` | строка | да | входной пин приёмника |
| `customNodes` | массив | нет | определения своих узлов, см. ниже |

Переменная, на которую ссылаются `VarGet`/`VarSet`, но которой нет в
`variables`, создаётся автоматически с `init = 0`. Если одна и та же переменная
объявлена дважды, используется первое объявление.

Числа в `props` принимают десятичный вид, `0x` (hex) и `0b` (binary).
Отрицательных чисел нет: значение всегда u64.

## Пины

- `exec` — белый провод выполнения. У узла один вход и один выход, кроме
  `Branch` (два выхода: `true`, `false`). Вход `exec` может принимать несколько
  проводов: это нужно для слияния веток.
- `u64` — голубой провод данных. Вход данных принимает ровно один провод.
  Выход данных может идти в несколько мест.

Данные не вычисляются заранее. Компилятор идёт от потребителя назад по проводам
и вставляет код прямо перед использованием. Поэтому один и тот же узел может
вычислиться несколько раз, если его значение нужно в разных местах. Если нужен
один результат на несколько потребителей, сохраните его в переменную.

## Узлы

### Flow control

| Узел | Входы | Выходы | Поведение |
|---|---|---|---|
| `Entry` | — | `exec` | точка входа. Ровно один на граф |
| `Branch` | `exec`, `cond: u64` | `true: exec`, `false: exec` | `cond != 0` идёт в `true`, иначе в `false` |
| `Anchor` | `exec` | `exec` | голова цикла. Обратный провод разрешён только сюда |
| `Return` | `exec`, `value: u64` | — | завершает программу с кодом `value`; если не подключён — 0 |

`Branch` без подключённого выхода ведёт в неявный `return 0`.
`Entry` без продолжения тоже даёт `return 0` (с предупреждением).

### Data

| Узел | Входы | Выходы | Свойства |
|---|---|---|---|
| `Const` | — | `value: u64` | `value` — число |
| `VarGet` | — | `value: u64` | `name` — имя переменной |
| `VarSet` | `exec`, `value: u64` | `exec` | `name` — имя переменной |
| `BinOp` | `a: u64`, `b: u64` | `result: u64` | `op`: `add`, `sub`, `mul`, `div`, `and`, `or`, `xor`, `shl`, `shr` |
| `Cmp` | `a: u64`, `b: u64` | `result: u64` | `op`: `eq`, `ne`, `lt`, `le`, `gt`, `ge` |

`div` — беззнаковое деление. `Cmp` возвращает 0 или 1.
`shl`/`shr` используют младшие 6 бит второго операнда — как обычный сдвиг
на целевой платформе.

### Input / output

| Узел | Входы | Выходы | Свойства |
|---|---|---|---|
| `PrintU64` | `exec`, `value: u64` | `exec` | печатает число в десятичном виде и `\n` |
| `PrintStr` | `exec` | `exec` | `text` — строка; печатает её байты как есть |
| `Call` | `exec`, `a0..a3: u64` | `exec`, `result: u64` | `func` — имя символа |
| `Syscall` | `exec`, `a0..a3: u64` | `exec`, `result: u64` | `number` — номер сисколла |

`PrintStr` не добавляет `\n`. Байты строки известны на этапе компиляции и
лежат в секции данных под меткой `LstrN`.

`Call` передаёт аргументы в C-регистры (`x0..x3` на ARM, `rdi`, `rsi`, `rdx`,
`rcx` на x86) и сохраняет `x0`/`rax` как `result`. На macOS имя автоматически
получает префикс `_`, если его нет. На Linux-целях сборка идёт с
`-nostdlib -static`, поэтому функции libc не подключатся, пока вы не поменяете
линковку.

`Syscall` передаёт `a0..a3` и номер как есть. Номера сисколлов различаются:
Linux AArch64 `write = 64`, `exit = 93`; macOS AArch64 `write = 4`,
`exit = 1`. На x86-64 Linux `write = 1`, `exit = 60`; на macOS x86-64
`write = 0x2000004`, `exit = 0x2000001`.

### Low level

| Узел | Входы | Выходы | Свойства |
|---|---|---|---|
| `RegGet` | — | `value: u64` | `reg` — имя регистра |
| `RegSet` | `exec`, `value: u64` | `exec` | `reg` — имя регистра |
| `RawAsm` | `exec`, `a: u64`, `b: u64` | `exec`, `result: u64` | `text` — строки ассемблера |

`RegGet`/`RegSet` работают с физическими регистрами целевой платформы.
Неизвестное имя даёт предупреждение, но компилятор всё равно подставит его
в текст. `sp`, `fp`, `rbp`, `rsp` лучше не трогать: кадр стека сломается.

`RawAsm` вставляет текст как есть. `{a}` и `{b}` заменяются:

| Цель | `{a}` | `{b}` | `result` |
|---|---|---|---|
| AArch64 | `x0` | `x1` | `x0` после вставки |
| x86-64 | `rax` | `r10` | `rax` после вставки |
| AVR | `r24` (пара `r24:r25`) | `r22` | `r24:r25` |
| STM32 | `r0` | `r1` | `r0` после вставки |

На ESP и исходниках C/C++/C# узел `RawAsm` не поддерживается: там нет
ассемблерного текста, в который можно вставить строку. Валидатор выдаёт ошибку.

На AVR комментарии в `RawAsm` пишутся через `;`: `//` ассемблер avr-as не
принимает. Строки `{a}`/`{b}` заменяются на регистровые имена, поэтому
вставлять туда свои значения нужно с оглядкой на занятость `r24:r25`.

Строки, начинающиеся с `.` или заканчивающиеся `:`, вставляются без отступа —
так можно объявлять локальные метки и данные. Остальные строки получают отступ.
Ответственность за сохранность регистров, стека и синтаксис — на авторе графа.

Текст `RawAsm` не переводится между синтаксисами. Пример `add {a}, {a}, {b}`
работает на AArch64; для x86-64 та же операция пишется как `add {a}, {b}`,
потому что в Intel-синтаксисе `add` принимает два операнда. Один и тот же
`RawAsm`-узел для разных целей придётся дублировать.

### Other

| Узел | Входы | Выходы | Свойства |
|---|---|---|---|
| `Comment` | — | — | `text` — заметка на холсте, в код не попадает |

## Микроконтроллеры

Один граф компилируется под любую цель. Ниже — различия между семействами.

### AVR

Цель `avr-atmega328p` (синонимы `avr`, `atmega328p`, `arduino-uno`,
`arduino-nano`) собирает граф в прошивку Arduino Uno/Nano: ассемблер под
ATmega328P, `.elf`, `.hex` и `.bin`. Точка входа — `main`, её вызывает `crt0`
из avr-libc, поэтому `Entry` становится обычной функцией, а не стартовым кодом.

Значения на AVR — 16-битные: аккумулятор живёт в паре `r24:r25`, всё, что
больше `0xFFFF`, усекается (валидатор предупреждает). Переменные и временные
лежат в SRAM (`.section .bss`), строки — в `.section .data`.

| Узел | Входы | Выходы | Свойства |
|---|---|---|---|
| `McuPinMode` | `exec` | `exec` | `pin` 0–19, `mode`: `out`, `in`, `pullup` |
| `McuDigitalWrite` | `exec`, `value: u64` | `exec` | `pin` 0–19 |
| `McuDigitalRead` | `exec` | `exec`, `value: u64` | `pin` 0–19 |
| `McuDelayMs` | `exec`, `value: u64` | `exec` | busy-wait, миллисекунды |
| `McuDelayUs` | `exec`, `value: u64` | `exec` | busy-wait, микросекунды |
| `McuUartInit` | `exec` | `exec` | `baud` |
| `McuUartWrite` | `exec`, `value: u64` | `exec` | отправляет младший байт |
| `McuUartWriteStr` | `exec` | `exec` | `text` — строка в `.data` |
| `McuAdcRead` | `exec` | `exec`, `value: u64` | `channel` 0–7 (A0–A7) |
| `McuRegisterWrite` | `exec`, `value: u64` | `exec` | `address` — адрес в data space |
| `McuRegisterRead` | `exec` | `exec`, `value: u64` | `address` — адрес в data space |

Номера пинов — Arduino, не порты:

| Пины | Порт | Пример |
|---|---|---|
| 0–7 | PORTD / DDRD / PIND | 0 — PD0 |
| 8–13 | PORTB / DDRB / PINB | 13 — PB5, встроенный светодиод Uno |
| 14–19 | PORTC / DDRC / PINC | 14 — PC0, он же A0 |

Прошивка занимается UART0, если в графе есть `PrintU64`, `PrintStr`,
`McuUartWrite`, `McuUartWriteStr` или `McuUartInit`. Без явного
`McuUartInit` пролог включает 9600 бод, 8N1; явный узел переопределяет
скорость (16 МГц, normal speed, `UBRR = 16e6/(16·baud) − 1`).

`PrintU64` и `PrintStr` на AVR тоже выводят в UART, а не в stdout.

Полезные адреса ATmega328P (data space):

| Регистр | Адрес | Регистр | Адрес |
|---|---|---|---|
| PINB / DDRB / PORTB | 0x23 / 0x24 / 0x25 | PIND / DDRD / PORTD | 0x29 / 0x2A / 0x2B |
| PINC / DDRC / PORTC | 0x26 / 0x27 / 0x28 | UCSR0A / UCSR0B / UCSR0C | 0xC0 / 0xC1 / 0xC2 |
| UBRR0L / UBRR0H / UDR0 | 0xC4 / 0xC5 / 0xC6 | ADMUX / ADCSRA / ADCL / ADCH | 0x7C / 0x7A / 0x78 / 0x79 |

`RegGet`/`RegSet` на AVR работают с `r0..r31`. Не трогайте `r1` (нулевой
регистр после умножения), `r28`/`r29` (Y) и `r30`/`r31` (Z): кодогенератор
использует их для строк.

На AVR недоступны `Call`, `Syscall` и свои узлы: у них нет шаблонов под AVR,
валидатор выдаёт ошибку. Это не ограничение реализации, а разница платформ:
у микроконтроллера нет операционной системы и хостового ABI.

### Сборка и прошивка

```bash
# скомпилировать в .elf/.hex/.bin
wireasm examples/avr_blink.json --build --out-dir out

# загрузить в плату через загрузчик Arduino
wireasm examples/avr_blink.json --flash /dev/cu.usbmodem14101 --board uno

# какие порты похожи на Arduino
wireasm --ports
```

Сборка идёт через `avr-gcc -mmcu=atmega328p -DF_CPU=16000000UL -Os`, загрузка —
через `avrdude -c arduino` (Uno — 115200 бод, Nano — 57600). В WireStudio это
`Microcontroller ▸ Build firmware` (F6), `Microcontroller ▸ Flash` (F7) и
`Microcontroller ▸ Board settings…`.

### STM32

Цель `stm32f411` (синонимы `stm32`, `stm32f4`, `cortex-m4`, `blackpill`)
даёт bare-metal Thumb-2 ассемблер: таблица векторов, `Reset_Handler`, `main`,
встроенные подпрограммы и линкерный скрипт. Чип стартует от внутреннего HSI
16 МГц, без libc и startup-файлов.

| Узел | Отличие от AVR |
|---|---|
| `McuPinMode` | свойства `port` (`A`–`H`) и `pin` (`0`–`15`), плюс `mode` |
| `McuDigitalWrite` / `McuDigitalRead` | те же `port` + `pin` |
| `McuAdcRead` | `channel` 0–15 (внешние каналы 0–7 на PA0–PA7) |
| `McuRegisterWrite` / `McuRegisterRead` | 32-битный адрес, например `0x40023830` |
| `RegGet` / `RegSet` | `r0..r12`, `sp`, `lr`, `pc` |

USART2 работает на PA2 (TX) / PA3 (RX), `PrintU64` и `PrintStr` пишут туда же.
`McuUartInit` задаёт baud для USART2. Задержки идут через SysTick.

Сборка: `arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -nostdlib` с линкерным
скриптом из `toolchain.rs`; на выходе `.elf`, `.hex`, `.bin`. Загрузка:
`--flash stlink` (`st-flash`) или `--flash dfu` (`dfu-util`).

### ESP32 и ESP8266

Цели `esp32` и `esp8266` переводят граф в скетч Arduino: `setup()` и `loop()`,
`pinMode`, `digitalWrite`, `delay`, `Serial`, `analogRead`. Номер пина — один
(0–39 у ESP32, 0–16 у ESP8266). Сборка — `arduino-cli compile` с FQBN
`esp32:esp32:esp32` или `esp8266:esp8266:nodemcuv2`; ядро должно быть
установлено (`arduino-cli core install …`). Загрузка — `arduino-cli upload`
на указанный порт.

### C, C++ и C#

Цели `c`, `cpp` и `csharp` дают обычный исходник с `main()`: данные
подставляются выражениями, поток выполнения — метками и `goto`. Это удобно,
чтобы посмотреть, во что превращается граф, и собрать его системным
компилятором (`cc`, `c++`) или `dotnet`. `Call` здесь разрешён — это вызов
функции стандартной библиотеки; `Syscall`, `RawAsm` и свои узлы — нет.
Сгенерированный файл открывается во вкладке кода WireStudio.

## Свои узлы

Свой узел описывается в массиве `customNodes` графа. В редакторе WireStudio он
создаётся через `Nodes → New custom node…`; в JSON выглядит так:

```json
{
  "kind": "lib_double",
  "title": "Double",
  "category": "Math",
  "description": "Умножает вход на два",
  "inputs":  [{ "name": "value", "type": "u64" }],
  "outputs": [{ "name": "result", "type": "u64" }],
  "asm": {
    "aarch64": "lsl {out}, {in0}, #1",
    "x86_64": "mov rax, rdi\nshl rax, 1"
  }
}
```

Поля:

| Поле | Смысл |
|---|---|
| `kind` | уникальный тип узла; буквы, цифры, `_`, `-`; не совпадает со встроенным |
| `title` | название в палитре и на холсте |
| `category` | группа в палитре (в 0.4.0 свои узлы показываются в разделе Custom) |
| `description` | пояснение для человека |
| `inputs`, `outputs` | пины `{ "name": ..., "type": "exec" \| "u64" }` |
| `asm.aarch64`, `asm.x86_64` | шаблоны ассемблера для двух архитектур |

Шаблон подставляется в код узла. Плейсхолдеры:

| Плейсхолдер | Значение |
|---|---|
| `{in0}`..`{in7}` | входы `u64` по порядку |
| `{a}`, `{b}` | первые два входа `u64` |
| `{out}` | регистр результата |
| `{label}` | уникальный префикс для локальных меток |
| `{prop:key}` | свойство экземпляра узла из `props` |

Регистровый контракт:

| Архитектура | Входы | Результат |
|---|---|---|
| AArch64 | `x0`..`x7` | `x0` |
| x86-64 | `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`, `r10`, `r11` | `rax` |

Если у узла есть `exec`-вход, он выполняется в потоке и может иметь `exec`-выход.
Без `exec`-входа это чисто вычислительный узел: он вычисляется там, где нужно его
значение. В версии 0.4.0 допустимы не больше 8 входов `u64`, не больше одного
выхода `u64`, не больше одного `exec`-входа и одного `exec`-выхода; `exec`-выход
требует `exec`-входа.

Шаблон вставляется как есть. Автор узла отвечает за сохранность регистров,
стека и синтаксис. Текст не переводится между архитектурами: для x86-64
`add` принимает два операнда, для AArch64 — три.

### Библиотеки узлов

Файл `*.wirelib.json` — это набор определений:

```json
{
  "format": "wireasm-library",
  "version": "1",
  "name": "WireASM math",
  "description": "Пара полезных узлов",
  "nodes": [ /* те же объекты, что и в customNodes */ ]
}
```

`File → Import node library…` заменяет определения с совпадающим `kind` и
добавляет остальные. `File → Export node library…` выгружает все свои узлы
текущего графа. Пример — `examples/wirelib_math.wirelib.json`.

`File → Import .s as node…` создаёт определение из готового ассемблерного файла
с пинами по умолчанию (`exec`, `value` на входе; `exec`, `result` на выходе).
Пины и шаблоны нужно проверить вручную.

## Циклы

Обратный провод по `exec` разрешён только в `Anchor`. Это проверяется
валидатором: если Branch или другой узел замыкает поток на себя, компиляция
остановится с ошибкой.

Схема цикла:

```
Entry → init → Anchor → условие → Branch ─false→ Return
                    ↑                  │
                    └── тело ←────────┘ true
```

На ассемблере Anchor — это метка. Branch даёт условный переход, конец тела —
безусловный переход на метку Anchor.

## Переменные

Переменные лежат в кадре стека. На AArch64 слоты адресуются от `sp` с
положительным смещением, на x86-64 — от `rbp` с отрицательным. Начальные
значения записываются в прологе функции.

Имена переменных не обязаны быть объявлены заранее, но объявление задаёт
`init`. Если имя встречается в `variables` и в узле с разным регистром, это
разные переменные.

## Валидатор

Ошибки останавливают генерацию:

- нет Entry или их больше одного;
- неизвестный `kind` или несуществующий пин;
- несовпадение типов на проводе;
- больше одного провода на вход данных;
- больше одного провода с выхода `exec`/`true`/`false`;
- не подключён обязательный вход (`cond`, `a`, `b`, `value`);
- пустое или неверное число в `Const`, пустой номер `Syscall`;
- пустое имя переменной, функции, регистра;
- цикл по данным;
- цикл по exec без Anchor;
- граф ссылается на отсутствующий узел;
- на AVR: пин вне 0–19, неизвестный режим пина, канал АЦП вне 0–7,
  нулевой baud, адрес вне 0..0xFFFF;
- на STM32: порт вне A–H, пин вне 0–15, канал АЦП вне 0–15, неизвестный
  регистр (кроме `r0..r12`, `sp`, `lr`, `pc`), адрес вне 32 бит;
- на ESP32: пин вне 0–39, на ESP8266 — вне 0–16;
- на MCU и исходниках: `Call`/`Syscall`/свой узел (кроме `Call` в C/C++/C#),
  `RawAsm` на ESP и в исходниках.

Предупреждения не мешают генерации:

- узел недостижим от Entry;
- Entry без продолжения;
- неизвестный регистр для выбранной цели;
- на AVR: `Const` больше `0xFFFF` (значение усечётся), baud выше 115200;
- на STM32 и ESP: `Const` больше `0xFFFF_FFFF` (значение усечётся до 32 бит).

## Цели

| Значение `target` | Синонимы | Точка входа |
|---|---|---|
| `aarch64-macos` | `arm64-macos`, `arm64-darwin` | `_main` |
| `aarch64-linux` | `arm64-linux` | `_start` |
| `x86_64-linux` | `x86-64-linux`, `amd64-linux` | `_start` |
| `x86_64-macos` | `x86-64-macos`, `amd64-macos` | `_main` |
| `avr-atmega328p` | `avr`, `atmega328p`, `arduino-uno`, `arduino-nano` | `main` |
| `stm32f411` | `stm32`, `stm32f4`, `stm32f411ce`, `cortex-m4`, `blackpill` | `main` |
| `esp32` | `esp-wroom-32`, `esp32-wroom` | `main` |
| `esp8266` | `nodemcu`, `esp-12` | `main` |
| `c` | `c99`, `c11` | `main` |
| `cpp` | `c++`, `cxx`, `cplusplus` | `main` |
| `csharp` | `c#`, `cs`, `dotnet`, `c-sharp` | `Main` |

Цель можно переопределить флагом CLI `--target`, не меняя JSON. В IDE —
выпадающим списком в шапке; при смене цели граф помечается изменённым.

## Ограничения версии 0.4.0

- Только u64. Нет знаковых, float, строк как значений, массивов, структур.
- На AVR значение фактически 16-битное (`r24:r25`); на STM32 и ESP —
  32-битное. Арифметика шире этих разрядов не поддерживается.
- Нет функций, определяемых в графе. `Call` зовёт внешний символ; на MCU он
  недоступен, в C/C++/C# — работает.
- ESP и исходники C/C++/C# не поддерживают `RawAsm` и свои узлы.
- Свои узлы: до 8 входов `u64` и один выход `u64`; вложенные свои узлы не
  поддерживаются.
- Нет проверки, что `RawAsm` не портит кадр стека.
- Нет отладки и трассировки.
- Выражения глубже 60 узлов дают ошибку кодогенерации.
- Комментарии и координаты хранятся в JSON, но на код не влияют.

## Формат схемы (0.4.0)

Схема — отдельный документ, не граф. Файл с полем `"kind": "wireasm-circuit"`
читается и IDE, и командой `wiresim`.

```json
{
  "kind": "wireasm-circuit",
  "version": "1",
  "name": "divider",
  "parts": [
    { "id": "V1", "kind": "vsource", "x": -190, "y": 0, "value": 12 },
    { "id": "R1", "kind": "resistor", "x": -60, "y": 0, "value": 10000 },
    { "id": "GND1", "kind": "ground", "x": 70, "y": 90 }
  ],
  "wires": [
    { "a": { "part": 0, "pin": "1" }, "b": { "part": 1, "pin": "1" } }
  ],
  "probes": [
    { "part": 1, "pin": "2", "name": "out" }
  ],
  "analysis": "dc",
  "dt": 1e-4,
  "stop": 2e-3,
  "mcu": false,
  "mcu_vdd": 3.3
}
```

| Поле | Смысл |
|---|---|
| `parts[].kind` | `resistor`, `capacitor`, `inductor`, `vsource`, `isource`, `diode`, `led`, `switch`, `gate`, `mcu_pin`, `ground` |
| `parts[].value` | номинал: Ом, Ф, Г, В, А; для `gate` — питание |
| `parts[].value2` | номинальный ток светодиода |
| `parts[].gate` | тип логики: `and`, `or`, `nand`, `nor`, `xor`, `xnor`, `not`, `buffer` |
| `parts[].pin` | имя вывода МК для `mcu_pin` (`C13`, `13`, …) |
| `parts[].wave` | форма источника: `dc`, `sine`, `pulse` |
| `parts[].amp`, `freq`, `duty` | амплитуда, частота и заполнение источника |
| `wires[]` | соединение двух выводов; выводы задаются индексом части и именем |
| `probes[]` | щуп на выводе, его имя попадает в легенду осциллографа |
| `analysis` | `dc`, `tran` или `ac` |
| `dt`, `stop` | шаг и длительность переходного процесса |
| `fstart`, `fstop`, `points` | границы и число точек АЧХ |
| `mcu`, `mcu_vdd` | гонять граф как виртуальный МК и его питание логики |

Имена выводов: у двухполюсных компонентов `1` и `2`, у логики `a`, `b`, `y`
(у инвертора `a` и `y`), у вывода МК `p`, у земли `0`.

Выводы соединяются в цепи алгоритмом объединения (union-find). Все выводы
земли — узел `0`. Остальные цепи получают имя автоматически: имя щупа, если
он есть, иначе имя вывода МК, иначе `R1_2` (часть и вывод). Пробелы и
небуквенные символы заменяются на `_`, имя с цифры в начале получает
префикс `n`.

Из схемы получается нетлист — тот же формат, что у `examples/sim_*.json`.
Экспорт: File → Export netlist… в IDE или `wiresim` для расчёта из терминала.

## Как читать сгенерированный `.s`

Файл начинается с шапки: версия, имя графа, цель, точка входа, число узлов и
проводов. Дальше идут:

1. пролог: сохранение `fp/lr` или `rbp`, выделение кадра, инициализация переменных;
2. блоки узлов с метками `L<id>`;
3. неявный `Ldefault_ret` — `return 0`;
4. `print_u64`, если в графе есть `PrintU64`;
5. вставленные шаблоны своих узлов с метками `Lcustom_*`;
6. секция данных со строками `LstrN`.

Метки и имена символов зависят от `id` узла. Меняйте `id` только если готовы
к тому, что адреса в отладчике изменятся.

На AVR файл устроен иначе: `main`, затем метки `L<id>`, затем `Ldefault_ret`
с `ret`, встроенные подпрограммы (`uart_write_byte`, `uart_write_str`,
`uart_print_u16`, `delay_ms`, `delay_us`, `udiv16`) и секции `.data`/`.bss`.
Переменные — `V<имя>_<хеш>`, временные выражения — `Wtmp0..Wtmp63`,
аргументы `RawAsm` — `Warg0`/`Warg1`.

STM32-файл начинается с `.syntax unified`, `.cpu cortex-m4`, `.thumb`, затем
таблица векторов (`_vectors`), `Reset_Handler`, `Default_Handler` и `main`.
Подпрограммы (`uart_write_byte`, `uart_write_str`, `uart_print_u32`,
`delay_ms`, `delay_us`, `udiv32`) эмитятся только если нужны графу. Все
ветки помечены `.thumb_func`, иначе линковщик ругается на `Unknown
destination type (ARM/Thumb)`. Переменные — `.bss`, строки — `.rodata`
байтами. ESP-файл — обычный `.ino` с `setup()`/`loop()` и комментариями `//`.
